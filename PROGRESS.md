## Decisions made

- Package manager: **pnpm**, pinned to `11.25.0` via corepack (`devEngines.packageManager` + `packageManager` fields).
- Workspace layout: `apps/*` for deployable applications, `packages/*` for shared/internal libraries.
- Module system: root `package.json` set to `"type": "module"`.
- `apps/web`: **real TypeScript**, not JS+JSDoc (see "TS rewrite" above for the reasoning/history). ESLint/Prettier/Storybook still deliberately skipped.
- `packages/types` written in `.ts`, not `.d.ts` — can grow real runtime exports later without restructuring.
- `packages/types` build output setup ("Option A"): compiles to `dist/` for the eventual case of a plain-Node consumer with no bundler, while `apps/web` (Vite-based) resolves straight from source via the `"development"` export condition, avoiding a rebuild-on-every-edit dev loop.
- `pnpm add` without an explicit version prefers a version already resolved elsewhere in the workspace lockfile over always grabbing npm's `latest` tag (this is why `packages/types`' `typescript` devDependency resolved to `^6.0.3`, matching `apps/web`, rather than the actual current npm-latest `7.0.2`) — kept deliberately, values workspace consistency over chasing newest.
- `PROGRESS.md` itself is intentionally **not committed** to git (author's choice) — lives as local working notes only; `.gitignore` briefly had a stray entry for it (from an unrelated edit) which has since been removed, but the file was never actually tracked in any commit regardless.

- [x] **Multi-module linking figured out the hard way — real lesson, worth remembering in full:**
  - Go modules can't nest (a directory tree belongs to exactly one module, nearest `go.mod` wins), so `packages/go-types` needed its own `go.mod`, separate from `apps/api-go-name-generator`'s.
  - Added **`go.work`** at the repo root (`go work init ./apps/api-go-name-generator ./packages/go-types`) — this alone was enough to make `go build`/`go run` resolve `go-types` locally, no `require`/`replace` needed at all for building.
  - But **`go mod tidy` and `go get` don't respect `go.work` the same way for a brand-new (never-required) cross-module import**: both try to _discover_ which module provides an unrecognized import via the network/proxy first, before ever consulting the workspace — and since `packages/go-types` is genuinely unpublished, that discovery is guaranteed to fail (it actually found the _real_ pushed `iob-exploring-monorepo` GitHub repo at a live pseudo-version and correctly reported it doesn't contain that subpackage).
  - A hand-written placeholder pseudo-version in `require` (`v0.0.0-00010101000000-000000000000`) does **not** fix this on its own — `go mod tidy` still tries to validate that the version is a real, fetchable revision and fails identically ("invalid version: unknown revision 000000000000").
  - **The actual fix needed both `require` and a `replace` directive together**: `replace github.com/.../packages/go-types => ../../packages/go-types`. `replace` is what makes resolution local and skips version validation entirely; `require` is what declares the dependency exists at all (a `replace` with no matching `require` does nothing). Once `replace` was in place, `go mod tidy` could even regenerate a missing/deleted `require` line on its own, correctly, no network involved — confirmed by deliberately deleting the `require` line and re-running `tidy`.
  - Net takeaway for next time a local cross-module Go dependency is needed: **add `go.work` for day-to-day building, and `require`+`replace` in the consuming module's own `go.mod` for that module to be self-sufficient/tidy-able on its own** (e.g. if built in isolation, outside the workspace, or in CI). They solve different problems; this repo now needs and has both.

### Lefthook design (decisions) and draft written to `lefthook.yml`

- **Fix order**: lint `--fix` → format → check (checks are read-only and see the final code). Fixers run sequentially (`parallel: false`) because they rewrite the same files.
- **Pre-commit: NO turbo** (user's call). Tools called directly on `{staged_files}` with a glob per language, `stage_fixed: true`. ESLint gets `--no-warn-ignored`; run from repo root so the root configs/ignores apply (the `--ignore-path` flags in package scripts are only needed because those run from inside a package). Go: `golangci-lint` is per package → one command per Go package with `root:`, skipped if no `.go` staged there. `golangci-lint fmt {staged_files}` for Go formatting.
- **Pre-push: checks only, through turbo, parallel.** Rejected fix forms on push: fixes made after committing modify the working tree, not the commits being pushed (would need a `git diff --exit-code` gate, and the fix tasks are uncached). Turbo's benefit here: cache shared with manual runs (a manual `lint:check` makes the push hook near-instant when nothing changed), `check` gets `^build` ordering, one summary. One turbo call with all three tasks (`lint:check format:check check`) rather than several parallel turbos, plus `format:root:check` as a separate command. `--continue` optional to see all failures; turbo otherwise aborts on first failure (the other packages print `Command failed` though they didn't fail).
- **Direct vs turbo rule**: direct where a file list makes it faster (staged files); turbo for whole-package tasks that are cacheable. Caveat noted: a direct `golangci-lint fmt` skips the Prettier half of the Go `format` script.
- **golangci-lint flags checked with `--help`**: `run` has `--new`, `--new-from-rev`, `--new-from-merge-base`, `--new-from-patch`, `--whole-files`, `--fix`. These only filter _reported_ issues (whole package still analysed, so no speedup); `--new` semantics are subtle (unstaged/untracked if any, else `HEAD~`). Not used.
