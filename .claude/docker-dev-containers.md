# Docker dev containers for a polyglot monorepo

## Problem

Running each service of a polyglot (multi-language) monorepo in its own container for local development — source bind-mounted from the host for hot-reload, an editor attaching to already-running containers (not the "reopen in container" flow) — while keeping the images generic/reusable, avoiding cross-platform correctness surprises, and not fighting the monorepo's own orchestrator (e.g. Turborepo) or package manager (e.g. pnpm) in the process.

## Chosen solution

- **One container per service**, not one monolithic container running everything. Each service's Dockerfile is fully generic; the compose file is the only place that supplies versions, working directory, port, and the actual startup command.
- **The whole repo is bind-mounted into every container**, not just each service's own subdirectory — this is required whenever the workspace/module system resolves sibling packages by relative path (pnpm's `workspace:*` symlinks, a Go `go.work`, etc.), even if a given container only runs one service.
- **The package manager's install step runs at container _start_, not at image build time.** A bind mount attaches _after_ the image is built, so anything an image's build step writes into the eventually-bind-mounted path is silently discarded the moment the container starts.
- **All caches/stores (package-manager content store, compiled-language module/build cache) live inside the bind-mounted tree, gitignored — not in separate Docker-managed named volumes.**

### Worked example: a Node + Go dev image

- **Base image: the JS/TS-ecosystem image (`node`), not the other language's image.** If a language's toolchain install is a simple, self-contained step (e.g. Go: download a tarball, extract it, done), it's less work to add that _into_ the JS-ecosystem image than to add Node + the package manager into the other language's image — installing Node usually needs a separate setup script, then the package manager's own bootstrap, on top of just getting a working shell. It also gets you a pre-built non-root user for free: official `node` images ship a `node` user at a fixed UID/GID (historically `1000:1000`), which most Linux dev-machine users already match — solving the classic "files created in the container are root-owned on my host" bind-mount problem without extra work. A non-JS base image (e.g. `golang`) typically ships root-only.
- **Version pin awareness**: pin to whatever's actually installed/used already, cross-checked against the current LTS/stable line — don't default to whatever a generic example happens to use, since that number drifts.
- **Toolchain-vendor churn is real and worth checking, not assuming**: Corepack (Node's former bundled pnpm/yarn activator) is being dropped from Node's own distribution starting at a specific major version, with older LTS lines keeping it only temporarily — verify current status rather than reusing old guidance, and prefer installing the package manager directly (`npm install -g pnpm@<version>`) if the bundled tool's future is uncertain.

## Reasoning

**Compose as the sole source of truth, Dockerfile fully generic:**

- A build-arg-driven Dockerfile (`ARG someVersion=` with an empty default, supplied only via the compose file's `build.args`) means the image is never accidentally built with an unintended silent default — an empty `ARG` used in `FROM` fails loudly ("invalid reference format") rather than resolving to something wrong.
- `WORKDIR`, `EXPOSE`, and `CMD` can all be deferred to the compose file (`working_dir`, `ports`, `command`) instead of baked into the image. `EXPOSE` in particular is pure documentation/metadata in the image — it does not publish anything by itself; a compose file's `ports:` mapping works completely independently of whether the image declares `EXPOSE` at all.
- This makes the same image genuinely reusable — a different compose service (or an unrelated project) can point the same image at a different directory, port, or command with zero Dockerfile changes.

**Ordering rules that actually matter inside a Dockerfile (unlike a declarative compose file, a Dockerfile executes top-to-bottom — order is execution order):**

- An `ARG` declared _before_ the first `FROM` is only in scope for that `FROM` line itself; using it later requires re-declaring `ARG <name>` _after_ `FROM` (no need to restate a default — it inherits the pre-`FROM` value).
- Anything that needs to write to a per-user config/home-relative path (installing a global tool, writing a user-level config file) must run _before_ `USER <non-root-user>` if it needs root, or _after_ if it needs to land in that user's own home.
- `$HOME` in an `ENV` line is resolved at the point that line executes, using whichever `USER` is currently active — not re-evaluated at container runtime. If a `PATH` (or similar) value is built from `$HOME/...`, that `ENV` line must come _after_ the `USER` switch, or it silently bakes in the wrong user's home directory.
- `ENV`/`ARG` substitution is plain text substitution referencing prior `ARG`/`ENV` values in the _same build_ — it is not a shell. Command substitution (`$(...)`) does not work in an `ENV`/`ARG` value.
- A downloaded archive piped into an extraction tool (`curl ... | tar ...`) must not also pass the extractor a literal filename — that tells it to open a file from disk (which was never saved, since nothing redirected `curl`'s output there), ignoring the pipe entirely. Either drop the filename argument so the extractor reads stdin, or drop the pipe and save-then-extract in two steps.
- A compose file's `command:` as a plain string is **not** run through a shell the way a Dockerfile's shell-form `CMD` is — it's tokenized into an argv array directly. Shell operators (`&&`, pipes, `;`) inside a plain-string `command:` are passed as literal arguments, not interpreted — wrap the chain in an explicit `sh -c "..."` (or use the list form `["sh", "-c", "..."]`) if a real shell is needed.
- A config-key's "supports config via environment variable" convention (e.g. npm-style `npm_config_<key>`) is not universal across every tool that superficially looks npm-compatible — verify empirically (inspect the running container/process) rather than assume it works for a given tool/key, and fall back to that tool's own native config mechanism (a config file, or an explicit CLI flag) if it doesn't.

**Fresh install at container start also solves cross-platform correctness, for free, if three things hold:**

- No process ever runs the package manager's install step directly on the host (only inside a container).
- The installed-dependencies directory is never committed to source control.
- Every service's startup command actually re-runs the install step every time, rather than trusting a possibly-stale copy.
- Given all three, the host's own OS/architecture becomes irrelevant to binary correctness (prebuilt native binaries, compiled native addons) — every platform-dependent decision happens inside the container, against the container's own platform, and a stale/wrong-platform `node_modules` (or equivalent) self-heals on the next install rather than needing to be prevented from occurring in the first place. Losing any one of the three conditions (e.g. optimizing away the "always reinstall" step later) reopens the risk.
- A package manager's own "already satisfies the lockfile, nothing to do" fast path means an install step can silently do nothing on a given run — don't assume a change (e.g. to where the content store lives) took effect just because the process exited cleanly; force a real install (delete the installed-dependencies directory) to actually observe new behavior.

**Cache/store placement — in-project bind-mounted directory, not a separate named volume:**

- A Docker named volume is a genuinely different filesystem/device than a bind-mounted directory. Some package managers' content-addressable stores rely on **hard links** (not copies) from the shared store into each project's own dependency tree for disk-space deduplication — hard links only work within a single filesystem/device. Moving such a store onto a separate volume silently breaks hard-linking; the package manager falls back to copying, which works but costs more disk space with no correctness benefit gained in return.
- A compiled language's module/build caches may have no such constraint at all — if the toolchain reads directly from the cache location rather than linking/copying into each project's tree, there's no efficiency argument for keeping it on a particular device, so it can live wherever is most convenient (a shared volume, or the same in-project directory as everything else) with no tradeoff either way.
- Placing caches inside the already-bind-mounted repo tree (as ordinary, gitignored subdirectories) sidesteps a real permission gotcha entirely: Docker auto-creates a _named volume's_ mount point as root, regardless of the container's configured `USER`, unless the image already has that exact path pre-seeded with correct ownership at build time. An ordinary directory inside an already-correctly-permissioned bind mount has no such mount-point-creation step at all — whichever user first needs it just creates it, already correctly owned.
- "Share one named volume across multiple, unrelated projects on the same machine" sounds like it recovers a global, cross-project deduplicated cache — it doesn't, once hard-linking is already broken by the volume/bind-mount device split described above. Every consuming project is still on a different device than that shared volume, so every one of them still falls back to copying; the only benefit that survives is avoiding a redundant _download_, not avoiding a redundant on-disk _copy_. Usually not worth the added complexity unless genuinely juggling several such projects at once.
- If more than one such cache location needs to be redirected in the same image, drive them all off a single build-arg for the cache root, with each specific sub-path built by simple string concatenation inside the Dockerfile — one value to change, one place a future consuming service overrides.
- A relocatable output-directory-style variable (e.g. wherever a language's "install a tool globally" command puts its binaries) may not need its own explicit variable at all if it's _derived_ from another one you're already relocating (e.g. it defaults to `<root>/bin`) — moving the root alone can cover it for free. But don't assume every related variable follows that root; some caches are structurally independent defaults with no derivation relationship to the "obvious" root variable at all, and need their own explicit redirect regardless.
- **A package manager's own config-precedence for "where's the store" can be genuinely surprising, and every layer of it is worth verifying empirically rather than assumed:** a plain project-root dotfile config may silently not be read at all for a given key even though it works for others; a CLI "set config" command with no explicit scope flag may write to **both** a project file and the user's **global** config simultaneously, and the global one may take precedence over the project one — the opposite of the traditional project-beats-global convention. A relative path landing in that global file is a real footgun, since it then affects every unrelated project on the machine, resolved differently depending on wherever each of them happens to invoke the tool from. The one mechanism most likely to actually work cleanly and predictably: that tool's dedicated **workspace-level config file**, if it has one (e.g. `pnpm-workspace.yaml`'s own `storeDir` key) — already a real, committed, version-controlled file, applies uniformly to every consumer without a global-scope side effect.

**A build orchestrator can silently strip environment variables from the very processes it's supposedly just wrapping:**

- A monorepo task orchestrator (Turborepo-style) may default to a "strict" environment mode for reproducible caching — a task process only receives a small built-in OS-level allowlist plus whatever's explicitly declared as passthrough, everything else is filtered out before the task's real process even starts, silently. A tool-specific environment variable that's correctly set at the container level (confirmed via `docker inspect`, confirmed reaching a plain shell inside the container) can still never reach the actual task process if the orchestrator sits between them and doesn't know it should pass that variable through.
- Diagnosing this requires checking the _actual task process's_ real environment (e.g. reading its `/proc/<pid>/environ` on Linux), not just a fresh shell opened into the same container — a `docker compose exec` shell and the container's real, orchestrator-spawned task process are not guaranteed to see the same effective environment.
- Fix: explicitly declare the variable as passthrough in the orchestrator's own config (e.g. a global, not-affecting-the-cache-hash passthrough list), rather than something that only affects that one variable's value.

**One container per service vs. one container for everything — no universal right answer, only a real tradeoff:**

- _For_ per-service: an independent failure/restart boundary (one service's dev process crashing doesn't take down every other running service in the same container — real debugging-ergonomics value), and it rehearses whatever the eventual production deployment topology will actually be, if these services will ever be independently deployed/scaled for real.
- _Against_ per-service, once actually worked through: services in the same monorepo usually end up needing the _same_ bind-mounted repo, largely the _same_ toolchain image (a "different language, so isolate it" argument gets weaker once one language's tooling turns out to depend on another's runtime anyway — e.g. a compiled-language service still needing the JS-ecosystem's task runner installed to invoke its own dev script), and the _same_ shared caches — much of the isolation the split was meant to buy turns out to be shared concern instead. The monorepo's own task orchestrator typically already computes correct cross-package dev/build ordering **within a single process**, with no help needed from container boundaries at all; splitting across containers doesn't remove that ordering problem, it _duplicates_ it at the compose level (`depends_on` between services), and container-level `depends_on` usually only guarantees _start order_, not real readiness — a single container sidesteps that race entirely by construction.
- Given the tradeoff isn't clearly one-sided, this is a case where reasoning about it in the abstract has real limits — actually trying **both** approaches (not just building one and monitoring whether it hurts) is what it'd take to form a genuinely trustworthy opinion, since several of the "obvious" arguments on both sides turned out to be weaker or stronger than they looked only once actually worked through concretely (see above). Picking one to build out further now — especially if it's already substantially working — and deferring the other rather than blocking on a decision is reasonable, but worth being honest that it's a deferral, not a resolved judgment call.

**Bind mount vs. named volume — a performance question with an environment-dependent answer:**

- On native Linux (host and container both Linux, no VM in between), a bind mount and a named volume are implemented via the same underlying kernel mechanism — no meaningful I/O performance difference.
- The "bind mounts are slow" reputation specifically comes from Docker Desktop on macOS/Windows, where every container runs inside a lightweight Linux VM (Docker fundamentally needs a Linux kernel) — a bind mount has to cross a host-OS-to-VM filesystem-sharing layer (historically gRPC-FUSE, more recently virtiofs on macOS) that adds real overhead for workloads with huge numbers of small files (a JS dependency tree is the canonical example). A named volume avoids this because Docker stores its data natively inside the VM's own filesystem, with no cross-OS translation step.
- Relevant to plan for if the same setup is ever expected to run on a non-Linux host, irrelevant otherwise.

**A bind-mounted repo has _two different absolute paths_ pointing at the same files — host tooling and container tooling don't automatically agree on which one is "real":**

- A bind mount doesn't give a directory one canonical path; it gives the same underlying files a different absolute path depending on which side (host or container) is looking. Most of the time this doesn't matter — but any tool that _records_ an absolute path as part of its own bookkeeping (a package manager writing where it thinks its content store lives, for instance) will bake in whichever path was true for whoever ran it last.
- Consequence: alternating between running that tool from the host and from a container against the _same_ bind-mounted repo makes the tool see a "different" environment every time it switches sides — even though the physical files never changed — because the recorded path string differs. This can manifest as a repeated, seemingly one-off "this needs to be rebuilt/reinstalled" prompt that actually recurs every time you cross that boundary, not a one-time migration cost.
- This is a structural property of mixing host-invoked and container-invoked tooling against shared bind-mounted state, not a bug in the specific tool that happens to surface it. The two real fixes are architectural, not a config tweak: either commit fully to one perspective (an editor's "reopen/attach fully inside the container" flow, so the host's path view never enters the picture at all), or route whatever host-triggered tooling exists (git hooks, etc.) through the container instead of letting it run natively on the host against the same files.

**An editor attached fully inside a dev container needs more than the app itself needs — plan for this separately, don't discover it live:**

- The app's own Dockerfile is built around what the _service_ needs to run. An editor doing real development work from inside that same container (not just the app process) additionally needs: the language's/ecosystem's dev tooling actually present (check, don't assume — e.g. a base image may ship a version-control client but not a project-specific linter), and a path for whatever credentials development work requires that the app itself never needed (commit identity, push authentication).
- **SSH agent forwarding** is the preferred way to give a container push/pull access without ever placing private key material inside it: forward the _live connection_ to the host's already-running agent (its Unix domain socket), rather than bind-mounting the key file directly. A compromised dependency inside the container can ask the forwarded agent to sign something while the session is live, but can't exfiltrate the key for later, offline reuse — meaningfully safer than the alternative. Some editors' remote-development tooling can do this forwarding automatically (detecting a running local agent), which is worth checking for before hand-rolling a volume-mount version.
- This isn't equally simple everywhere: it depends on an agent already running with keys loaded, which is a default-on situation on some platforms and not others (a platform's SSH agent may ship as a disabled-by-default service needing manual setup first) — verify per-platform if this setup is ever expected to run somewhere other than where it was built.
- Don't assume commit signing is in play — check the actual config (a signing key, a signing-format setting, a sign-by-default flag) before treating it as a requirement to solve for; it may simply not be configured at all.

**Trust a third-party CLI tool's own documented install method over a generic "build it from the language's own tooling" shortcut, when the tool's own docs say so:**

- A language's native "fetch and compile this from source" mechanism (its package manager's own install-a-tool command) seems like the obvious, idiomatic way to provision any dev tool written in that language — and often is. But some tools explicitly document that this specific path isn't reliable for them: the resulting binary depends on whichever toolchain version happens to be present wherever it's built, isn't the exact artifact the tool's own CI validated, and isn't guaranteed to behave identically to an official release.
- When a tool says this about itself, prefer its own official distribution mechanism — typically a pinned, checksummed install script or a direct binary release — over the generic language-native shortcut, and pin its version explicitly the same way every other tool version in the image is pinned (a build arg, not a bare `@latest`/unpinned convenience command).
- The same bind-mount-vs-build-time placement rule applies to installing any such tool: its target directory must live outside the bind-mounted tree, or it silently vanishes the moment the real mount overlays that path at container start.

**A monorepo-wide check hook doesn't automatically compose with a "lean, single-service container":**

- A pre-push (or similar) hook that runs checks across an entire workspace assumes the environment it runs in can actually build/check every package — but a container purpose-built for one service may have only ever installed and built that one slice of the workspace. Running the full check suite from inside it will surface every other package's gaps at once, some of which may be entirely unrelated to each other and pre-existing (not caused by anything about the container).
- Before concluding a batch of failures shares one root cause, isolate: reproduce the most suspicious-looking one directly, bypassing the orchestrator (call the underlying tool binaries straight from wherever they're installed) to confirm whether it's genuinely one shared cause or several independent ones masquerading as a single failed run. A downstream package failing to resolve an import from a sibling package is often really that sibling's own build never completing, not a bug in the downstream package at all.
- This is a real, undecided design tension worth naming rather than working around silently: either scope workspace-wide checks down to what's actually relevant, or accept that any container expected to run them needs the _entire_ workspace installed and buildable, not just its own service's slice.

## How to

1. **Pick the base image**: whichever ecosystem has the simpler "install the other toolchain into me" story, usually the one with a pre-built non-root user already matching common host UID/GID conventions.
2. **Parameterize every version as an empty-default `ARG`**, supplied only via the compose file's `build.args` — verify each `ARG` is declared in a scope that actually reaches where it's used (after `FROM`, not just before it, if used post-`FROM`).
3. **Do root-requiring setup first** (global tool installs, extracting a toolchain into a system path), **then `USER <non-root>`**, **then anything that needs to write into that user's own home** (per-user config files, `$HOME`-relative `PATH` entries) — get the ordering right the first time by asking "does this need root, or does this need to end up owned by the non-root user" for each line.
4. **Defer `WORKDIR`/`EXPOSE`/`CMD` to the compose file** (`working_dir`/`ports`/`command`) unless there's a specific reason the image itself needs an opinion about them.
5. **Pick one root directory for every relocatable cache/store**, drive it from a single build-arg, and mount it as an ordinary path _inside_ the same bind mount as the rest of the repo — not a separate named volume — then gitignore it.
6. **Run the package manager's install step as part of the container's startup command, not a Dockerfile `RUN`** — verify this by actually deleting the installed-dependencies directory and confirming a fresh container repopulates it correctly, not just that a container starts without error.
7. **If a monorepo task orchestrator is involved, check its environment-variable-passthrough behavior explicitly** — don't assume a variable that's correctly set on the container reaches the actual task process; verify by inspecting the real task process's environment, not just an ad hoc shell in the same container.
8. **Verify configuration changes for real, not by "the command didn't error"**: rebuild after any Dockerfile change (a compose `up` without `--build` reuses an existing image even if the Dockerfile changed), and force a cold run (delete caches/dependencies) after any change to where something is supposed to be stored, since a package manager's "already up to date" fast path can mask a config change that never actually took effect.
9. **Decide up front whether developers will ever run the workspace's own tooling (installs, lint/format/test commands, git hooks) from the host at all, against the same bind-mounted repo a container also uses** — if yes, expect the absolute-path-divergence class of bug above, and plan for it (workspace-level config over per-path config, or committing fully to one side) rather than discovering it mid-session.
10. **If an editor will attach fully inside a container for real development, not just to view a running app**, separately provision whatever that requires beyond the app's own runtime — a version-control client, credential/agent forwarding, any dev tool a workspace-wide check suite depends on — before it's needed, not as a reactive fix once a command fails.
